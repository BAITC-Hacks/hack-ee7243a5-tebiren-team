# ТЗ: доведение Career Quest до требований HackAlem AI

Версия: 1.0. Дата: 23 сентября 2026 года.

Статус: основная реализация выполнена 23 сентября 2026 года; результаты и границы проверки — в [CORE_ACCEPTANCE.md](CORE_ACCEPTANCE.md). Ниже сохранено исходное согласованное ТЗ.

Основание: «HackAlem AI: Career Quest — платформа геймификации жизненного цикла сотрудника», раздел Career Quest, страницы 2–5, и аудит текущей реализации.

## 1. Цель и последовательность работ

Подготовить воспроизводимое приложение, в котором сотрудник получает обоснованные шаги развития, выполняет активность и видит корректное изменение навыков, а HR видит пробелы в компетенциях, участие и сотрудников без следующего шага.

Согласованная последовательность:

1. Подготовить настоящее ТЗ на основную функциональность.
2. Реализовать его и пройти приёмку.
3. Подготовить отдельное ТЗ на геймификацию с учётом готового ядра.
4. Реализовать и проверить геймификацию.

Настоящий этап не включает валюту, награды, магазин, бейджи, серии посещений и соревновательные механики. В задании хакатона геймификация необязательна. Публичные рейтинги сотрудников по результативности и очки за обязательные HR-процессы не допускаются.

## 2. Исходное состояние

На момент аудита:

- Загружаются 200 сотрудников, 40 событий и 60 навыков из стартового набора.
- Работают профиль, карьерная цель, история, подбор шагов, выполнение и базовый HR-экран.
- Реальные обращения к OpenAI подтверждены; один проверочный запрос рекомендаций занял 5,05 секунды. Это разовый замер, а не гарантия задержки.
- 14 имеющихся backend-тестов проходят; frontend собирается.
- Во всех 200 профилях подбор без LLM завершился без исключений. У 41 профиля нет подходящего шага; это само по себе не ошибка и требует объяснения причины.
- Обнаружены снижение навыков при выполнении отдельных активностей и потеря импортированных сотрудников из списка выбора из-за лимита 200.
- HR получает количество сотрудников без шага, но не их список; участие доступно общей статистикой, без разбивки по активностям.
- Авторизации, постоянного хранения изменений и единой команды запуска двух компонентов нет.

Прохождение существующих тестов не означает закрытие перечисленных дефектов. Сравнение результатов до и после исправления расчёта должно учитывать, что исходные вычисляемые навыки и проценты также могут измениться.

## 3. Границы и принятые решения

- Сохраняются React/TypeScript/Vite и FastAPI/Python, существующий дизайн и формат стартового набора.
- Backend является источником истины для навыков, допустимости событий, ранжирования, прогресса и прав доступа.
- Предлагаемый объём AI на этом этапе: многофакторный алгоритм выбирает шаги, OpenAI формулирует объяснения по проверенным фактам. LLM не меняет выбранные события, их порядок, числовые значения и правила роста.
- Добавление LLM-переранжирования не является условием приёмки этого этапа. ТЗ хакатона не предписывает выполнять весь подбор исключительно через LLM; в README и на защите фактическая роль AI описывается точно.
- Для сохранения локальных изменений используется SQLite. Это инженерная доработка для надёжности демонстрации, а не отдельное прямое требование PDF.
- Для локальной демонстрации предусматриваются две роли и тестовые учётные записи. Банковский SSO, production-развёртывание и промышленная система управления аккаунтами в этот этап не входят.
- Данные остаются синтетическими. Ключ OpenAI хранится только на backend и не входит в репозиторий или frontend-сборку.
- Дата снимка датасета остаётся единой для расчётов, истории и интерфейса. При текущем наборе это `2026-10-01`; вместо захардкоженной другой даты frontend получает значение от backend.
- Русская и казахская локализация, расширенная аналитика и интеграции с календарём не входят в обязательный объём этого этапа.

Приоритет P0 — исправления, без которых нельзя надёжно показать основной сценарий. P1 — остальные требования и доработки, необходимые для завершения настоящего этапа. Оба приоритета входят в его приёмку.

## 4. Функциональные требования

### CQ-01. Корректный рост навыков и прогресс — P0

Основание: обязательное обновление прогресса и правила роста из датасета.

Backend:

- Применять единое правило роста и в прогнозе рекомендации, и при выполнении, и при восстановлении навыков из истории.
- Для корректных входных уровней `0…5` использовать `after = max(before, min(5, activity.max_level, before + activity.gain))`. Потолок активности ограничивает прирост, но не уменьшает ранее достигнутый уровень.
- Соблюдать правила стартового набора о дате последней оценки, завершённых и повторяемых событиях. История до оценки не начисляет уже учтённый прирост второй раз.
- При неизменной цели выполнение активности не уменьшает ни один навык и общий процент готовности. Не обещать положительный прирост, если доступный прирост равен нулю.
- Повторный запрос завершения той же неповторяемой активности не создаёт вторую запись и не начисляет прирост повторно, включая параллельные запросы.
- Транзакционно сохранять завершение и возвращать фактические изменения навыков и прогресса.

Frontend: после успешного завершения обновлять профиль, историю и рекомендации; показывать фактическое изменение, например «System Design: 2 → 3».

Приёмка: случаи `E0070 + EV_008`, `E0014 + EV_037/EV_038` и проверки по всем рекомендованным событиям исходных 200 профилей не уменьшают навыки. Прогнозируемый прирост совпадает с фактическим при неизменном исходном состоянии.

### CQ-02. Импорт и доступность профилей жюри — P0

Основание: обязательная загрузка дополнительных профилей и истории на защите.

Backend:

- Принимать `employees.json` и `activity_history.csv` по схеме стартового набора: вместе или по отдельности, если ссылки на сотрудников корректны.
- Поддерживать UTF-8, включая BOM. Проверять обязательные поля, типы и диапазоны, даты, навыки, роль/грейд, карьерную цель, ссылки на события и дубликаты ID.
- Сохранять импорт атомарно: ошибка одной строки не должна оставлять частично импортированные данные.
- Сохранять действующую политику отказа при повторяющихся ID с понятной ошибкой; не перезаписывать существующий профиль молча.
- Возвращать количество добавленных записей, предупреждения и ID добавленных сотрудников.
- Добавить серверный поиск и пагинацию сотрудников со стабильным порядком и общим количеством результатов. Исключить недоступность записей после первых 200 или 500.

Frontend:

- Использовать серверный поиск по ID/имени/роли и загрузку следующих страниц в HR-списке выбора.
- После импорта показывать результат, предупреждения и действие «Открыть профиль» для добавленных сотрудников.
- Выводить конкретную причину отказа и номер строки/имя поля, когда они известны.
- При импорте истории обновлять затронутый открытый профиль и HR-данные.

Приёмка: импортированный `E9001` доступен через интерфейс, профиль и рекомендации без перезапуска. Некорректный файл ничего не меняет. Корректный импорт истории влияет на расчёт и обоснование.

### CQ-03. Проверяемые объяснения рекомендаций — P0

Основание: минимум три фактора в обосновании; несколько пунктов об одном навыке не считаются тремя независимыми факторами.

Backend формирует факты до вызова LLM:

- Текущие роль и грейд, целевые роль и грейд.
- Текущий и требуемый уровень навыка, разрыв и критичность для цели.
- Допустимость активности для сотрудника и прогнозируемый эффект по правилам датасета.
- Конкретная релевантная история: количество завершений, пропусков, отказов и незавершённых событий; явно определённый критерий похожести активностей.

Каждая непустая рекомендация сопровождается минимум тремя различимыми основаниями из требований: текущий грейд, разрывы навыков, история участия, требования следующего уровня. Если истории нет, это указывается честно; нельзя приписывать успешное прохождение или пропуски. Для таких профилей обоснование опирается на остальные доступные факторы.

OpenAI получает минимальный набор этих фактов без ФИО и других ненужных персональных полей. Текст из импортируемого датасета рассматривается как данные, а не инструкции.

Обязательные структурированные основания и цифры формирует backend; свободный текст AI служит дополнением. Нельзя заменять проверенные основания произвольными LLM-утверждениями. При ошибке формата, посторонних ID или выявленном противоречии с фактами используется детерминированное объяснение.

Frontend показывает целевой переход, проверяемые основания и ожидаемые изменения навыков. В обычном пользовательском сценарии не нужны SDK-названия, JSON и другие технические детали.

Приёмка: профиль с низким Public Speaking, пропусками похожих мероприятий и критичным System Design получает объяснение, которое учитывает эти обстоятельства. AI не заявляет о завершённых похожих курсах без подтверждающих данных. Отдельно проверяется профиль без истории.

### CQ-04. Полный обязательный HR-view — P0

Основание: проседающие навыки, сотрудники без рекомендованного шага и участие по активностям.

Backend дополнительно возвращает:

- Список сотрудников без шага: ID, имя, роль, грейд, цель и код/текст причины. Количество согласуется с общим числом записей списка, учитывая пагинацию.
- Участие по каждой активности: ID, название, число уникальных участников и количества записей по всем статусам `completed`, `in_progress`, `dropped`, `no_show`, `declined`, `overdue`.
- Общие показатели с определёнными знаменателями. Повторное участие не должно ошибочно считаться несколькими уникальными людьми.

Frontend показывает таблицу/диаграмму участия и список сотрудников с переходом к профилю. Отсутствие карьерной цели, достижение требований и отсутствие подходящего события обозначаются разными причинами; все такие люди не объявляются автоматически «выпавшими из развития».

Существующий декоративный фильтр `All departments` убрать до появления работающей фильтрации. Общий срез по всем подразделениям достаточен для этого этапа.

Приёмка: из HR можно открыть конкретного человека без шага, понять причину и сравнить статусы участия по событиям. Суммы по статусам совпадают с соответствующей историей. Сводка не вызывает OpenAI для каждого сотрудника.

### CQ-05. Пустые состояния и ошибки frontend — P0

Основание: работоспособность основного сценария.

- Разделять состояния: рекомендация ещё не запрошена, загрузка, рекомендации найдены, подходящих шагов нет, запрос завершился ошибкой.
- Сохранять и показывать причину пустого результата из backend: нет цели, требования уже выполнены, нет допустимой активности.
- Обрабатывать ошибки списка сотрудников, профиля, рекомендаций, импорта и выполнения с понятным сообщением и возможностью повторить действие.
- Блокировать повторное отправление завершения до ответа. Если завершение сохранено, а обновление рекомендаций не удалось, не предлагать выполнить активность повторно: показать успех и отдельно повторить загрузку.
- При смене сотрудника устаревший ответ предыдущего запроса не должен перезаписывать новый профиль или его рекомендации.
- Понятно обрабатывать истёкшую сессию и недоступность backend.

Приёмка: пустой результат перестаёт возвращать пользователя к той же кнопке без объяснения; сбои сети и быстрые переключения профилей не смешивают данные сотрудников.

### CQ-06. Роли сотрудник / HR и приватность — P1

Основание: прямые требования задания о разграничении доступа и приватности.

Для демонстрации реализовать вход с двумя ролями и серверной сессией. Предусмотреть локальные тестовые аккаунты HR и сотрудника; данные для входа задаются при локальной настройке. Клиент не назначает себе роль или employee_id самостоятельно. Пароли в хранилище не должны храниться открытым текстом, секреты не коммитятся.

| Действие | Сотрудник | HR |
|---|---|---|
| Просмотр профиля и истории | Только свои | Все доступные в демо |
| Получение рекомендаций | Только свои | Для выбранного сотрудника |
| Отметка выполнения | Только своя | Для выбранного сотрудника, как демо-симуляция |
| Общий список сотрудников, HR-summary | Нет | Да |
| Импорт и сброс демонстрационных данных | Нет | Да |

Проверки прав обязательны на API, а не только в меню. Без сессии защищённый запрос возвращает `401`, при недостаточных правах — `403`. Logout прекращает действие сессии. Сессионный cookie недоступен JavaScript; изменяющие запросы защищаются от CSRF. CORS ограничен настроенными доверенными origin.

Приёмка: сотрудник не читает чужую историю через прямой URL, не вызывает HR/import/reset и не меняет чужой прогресс подстановкой ID. В HR-сессии сценарий импорта и проверки профилей жюри работает.

### CQ-07. Сохранение изменений — P1

Основание: инженерная надёжность демонстрации; это расширение, не отдельный must-have из PDF.

- Сохранять добавленных сотрудников, импортированную историю и новые завершения в SQLite отдельно от исходного набора.
- После перезапуска восстанавливать то же логическое состояние без повторного начисления навыков и дубликатов записей.
- Не изменять исходные JSON/CSV. Тесты используют отдельную временную БД.
- Сброс доступен HR с явным подтверждением: он удаляет импорт и симуляции выполнения и возвращает исходный набор. Не запускать его автоматически при старте или при проверке здоровья.
- Файл БД и локальные секреты исключить из Git; документировать расположение и способ резервного копирования БД перед сбросом.

Приёмка: после импорта и выполнения перезапуск сохраняет профиль, историю и прогресс. Сброс меняет только демонстрационные данные, не исходные файлы.

### CQ-08. Время ответа и устойчивость OpenAI — P1

Основание: интерфейс до 2 секунд, AI-рекомендация до 10 секунд.

- При запуске запроса сразу показывать состояние загрузки и сохранять отзывчивость интерфейса.
- Установить общий бюджет запроса рекомендаций: backend возвращает результат или детерминированный fallback не позднее 9 секунд, оставляя запас для доставки и отрисовки.
- Отдельно ограничить время OpenAI в пределах общего бюджета. Не допускать повторных SDK-попыток, которые превышают его; использовать `max_retries=0` либо эквивалентную контролируемую стратегию.
- Ошибка ключа, квоты, сети, некорректный ответ и таймаут не лишают пользователя алгоритмических рекомендаций и проверенных объяснений.
- Сохранять `explanation_source`; писать техническую причину fallback в журнал без ключей, токенов и полного содержимого профилей.
- `openai_enabled` означает наличие конфигурации. Успешность обращения подтверждается результатом с `explanation_source=openai`; health-проверка не делает платный запрос к модели.

Приёмка: отдельные проверки успешного OpenAI-ответа, отсутствующей конфигурации, 401/429 и зависшего провайдера. Для всех сценариев соблюдается общий бюджет. Замеры интерфейса и запросов фиксируются на машине демонстрации; запуск зависимостей и cold start сервера в эти показатели не входят.

### CQ-09. Понятный прогресс и сведения об активности — P1

Основание: объяснимость продвижения и пользовательская ценность.

- Добавить краткое объяснение процента готовности: покрытие требований целевой роли с весом 1,5 для критичных навыков и 1 для остальных, округлённое до одного знака.
- Не выдавать готовность по навыкам за гарантию повышения. Текущий грейд не меняется автоматически при достижении 100%.
- Удалить представление внутреннего `score` как `Match N%`. Для пользователя показывать место шага и конкретную пользу; технический score может оставаться в API.
- Передавать существующие в каталоге тип, формат, длительность и ближайшую доступную дату события. Не выдумывать отсутствующие значения.
- Использовать единую дату снимка из backend на экране профиля.

Приёмка: можно понять, откуда взялся процент и что изменит активность; невысокий внутренний score не выглядит как «курс подходит на 6%».

### CQ-10. Запуск и документация — P1

Основание: запуск одной командой, README и воспроизводимость; в критериях хакатона документация и воспроизводимость оцениваются в 25 баллов.

- После описанной первоначальной установки запускать frontend и backend одной командой из корня, целевой интерфейс — `npm run dev`.
- Сохранить отдельные команды запуска компонентов для отладки. Единый запуск корректно завершает только созданные им процессы.
- При занятом порте выводить понятное сообщение с действием для пользователя; не убивать неизвестные процессы и не запускать приложение с неработающим адресом API.
- Основной запуск использует реальный backend. Моки включаются только явно в отдельном режиме.
- Настройка локальных переменных и `.env` документирована и проверена для PowerShell. Backend действительно загружает поддерживаемый файл конфигурации; существующие настройки не перезаписываются запуском.
- Корневой README объединяет архитектуру, роль OpenAI, установку, настройку, роли доступа, импорт, запуск тестов, демо-сценарий, правила расчёта и известные ограничения.
- Зафиксировать проверенные версии зависимостей средствами lock-файлов/ограничений версий. Обеспечить повторяемую установку; не полагаться на неконтролируемые `latest`.
- Пример демонстрации выбирает реально допустимую рекомендацию, а не заранее указанный ID, который может нарушать prerequisites.

Приёмка: запуск из чистой копии репозитория на Windows по README, без ручных правок кода; профиль загружается с реального API. Без OpenAI основное приложение работает с fallback. Одно завершение запуска не затрагивает чужие процессы.

## 5. Контракты API и согласованность компонентов

Существующие маршруты по возможности сохраняются. Новые поля добавляются согласованно в Pydantic-схемы, TypeScript-типы, клиент нормализации, UI и тестовые данные.

| Контракт | Планируемые изменения |
|---|---|
| `GET /api/employees` | `search`, `limit`, `offset`; ответ `employees`, `total`, `limit`, `offset`; доступ HR |
| `GET /api/employees/{id}` | Проверка владельца/HR; рассчитанные навыки и актуальный прогресс |
| `POST /api/employees/{id}/recommendations` | Структурированные основания, сведения об активности, стабильный `reason_code` и текст для пустого результата |
| `POST /api/employees/{id}/complete` | Проверка прав, транзакция, отсутствие повторного начисления, фактические изменения |
| `GET /api/hr/summary` | Существующие агрегаты плюс участие по активностям; без LLM-вызовов |
| `GET /api/hr/employees-without-next-step` | Пагинированный список с причинами и общим количеством |
| `POST /api/import` | Атомарность, структурированные ошибки/предупреждения, `imported_employee_ids` |
| `POST /api/reset` | Доступ HR; сброс сохранённых демо-изменений, явное подтверждение в UI |
| `/api/auth/login`, `/api/auth/me`, `/api/auth/logout` | Вход, сведения о текущем пользователе и завершение серверной сессии |
| `GET /api/health` | Доступность без секретов; единая `dataset_as_of`; конфигурация OpenAI не равна проверенной связи |

Машинные коды ошибок и причин должны быть стабильными, а отображаемый текст — понятным. Конкретная JSON-форма структурированных оснований и ошибок фиксируется в API-схемах при реализации и проверяется контрактными тестами. Frontend не должен молча заменять обязательные данные пустыми массивами и скрывать несовместимость API.

## 6. Порядок реализации

|---|---|---|

| 2. Профили жюри | CQ-02 и относящиеся к импорту состояния CQ-05 | Новый профиль доступен и влияет на расчёты |
| 3. Качество рекомендаций | CQ-03, CQ-08, остальные состояния CQ-05 | Проверенные основания, fallback и соблюдение задержки |

## 7. Проверки и критерии завершения

Тестовые завершения, импорт и сброс выполняются в отдельном состоянии/БД, без очистки работающей пользовательской демонстрации.

| Проверка | Критерий |
|---|---|
| Регрессия | Имеющиеся тесты адаптированы к согласованным контрактам и проходят; frontend production-build успешен |
| Рост навыков | Граничные `gain/max_level`, история, повторное выполнение и все исходные профили проверены; снижения нет |
| Прогноз и выполнение | Числа в карточке совпадают с результатом при том же исходном состоянии |
| Импорт жюри | JSON + CSV, BOM, `E9001`, поиск за пределами первой страницы, дубликаты, неверные ссылки и атомарность |
| Сложные профили | Три локальных сценария: критичный навык против минимального с плохой историей; переход в другую роль; отсутствие истории/допустимого шага |
| Объяснения | Не менее трёх фактических категорий оснований при наличии рекомендации; нет выдуманной истории; target и current различаются |
| AI/fallback | Проверены реальный успешный ответ и имитации таймаута, ошибки ключа/квоты и некорректного ответа; порядок и цифры не меняются LLM |
| HR | Список и счётчик согласованы; участие по событиям совпадает с историей; переход к профилю работает |
| Доступ | 401/403, попытки подстановки employee_id, запрет HR/import/reset для сотрудника, logout, CSRF |
| Хранение | Перезапуск сохраняет импорт/завершение; сброс восстанавливает исходное демо; повторного начисления нет |
| Frontend | Пустые состояния, ошибки, смена сотрудника во время запроса и частичный сбой после успешного выполнения |
| Задержки | UI остаётся отзывчивым; основные экраны до 2 секунд на демо-машине; рекомендации с fallback до 10 секунд |
| Воспроизводимость | Чистая копия, задокументированная установка, единая команда запуска, правильный API-режим, отсутствие секретов в Git/сборке |

Локальные сложные профили не заменяют скрытые профили жюри и не являются обещанием их успешного прохождения. Они должны проверять разные факторы и ограничения, а не быть подстроены под конкретный event_id.

Этап считается завершённым, когда реализованы CQ-01…CQ-10, пройдены применимые проверки, а результаты и оставшиеся ограничения записаны в кратком отчёте проверки. В отчёте различать автоматические тесты, проверки API и проверки в браузере; непроверенное не обозначать как работающее.

## 8. Результаты этапа и переход к геймификации

Результат реализации: исправленный frontend/backend, обновлённые API-схемы и тесты, примеры проверочных профилей, единый запуск, корневой README и отчёт приёмки.

После завершения этого этапа готовится отдельное ТЗ на геймификацию.
